# Assistant 功能现状与开发方向

核对日期：2026-09-19。本文根据当前源代码、本地配置和现有测试整理；工作区仍包含尚未拆分提交的并行改动。

整理期间工作区出现其他来源的测试改动，涉及搜索身份规则、项目命名和 CLI 版本约束；本次未修改或验收那些并行改动。本文及 34 项测试结果对应本次读取的基线，相关实现合入后需重新核对。

## 1. 现状判断

这是一个飞书入口的团队 Agent 内部试用版本：Python 接收事件、路由权限和维护状态，Claude Code CLI 执行推理及工具调用，lark-cli 访问飞书资源。飞书业务大多由 Agent 调用 CLI 完成，没有为每项业务实现独立的确定性工作流。

核心链路已有实现；多用户身份、数据隔离、失败恢复和业务验收仍不完整。目前更适合在边界明确的小范围场景试用。

## 5. 优先处理的实际缺口

以下为代码检查结论或明确标注的待验证项，并非声称已在线复现所有故障。

### 优先级 0：多人使用前补边界

1. **身份与授权绑定。** `ensure_user` 不接收 sender；`_already_logged_in` 只检查 identity == user，没有校验登录用户、所需 scope 或当前调用身份。不同人会复用同一登录；并发不同 domain 也直接复用首个结果。建议先明确只支持一个固定身份，或设计逐用户隔离后再开放个人查询。
2. **会话和记忆隔离。** 会话只按 chat_id，群内多人共享；记忆没有 chat_id、sender 或资源权限过滤。建议区分项目共享记忆与个人记忆，召回时按权限过滤，模式变更使旧会话失效。
3. **管理指令权限。** 调度配置在 tier 判断前执行，没有管理员检查。推送目标和开关全局共享，普通用户可覆盖。应绑定管理员及群范围。
4. **工作区与工具权限。** cwd 及 CLAUDE.md 是约定，不能替代完整隔离验证；thesis/dev 目标目录不自动加载包内模板，而且尚未同步 docs 的禁止自行登录规则。P4 多群并发共用工作区也没有工作区级锁。先做权限矩阵和并发边界验收，再开放写代码/提交。

### 优先级 1：让已有流程可靠

- **调度跨月：** `_seconds_until` 使用 `replace(day=now.day + 1)`，月末且当天目标时间已过时会构造无效日期。
- **到期日期：** 用到期日零点减当前时间后取 `.days`，当天任务可能算逾期、明天任务可能算今天；应按明确的日期/时间语义比较。
- **业务错误与空数据：** 查询封装将若干错误折叠成空列表，摘要可能把权限失败写成“暂无任务”；应区分无数据、未授权和接口错误。
- **成功状态：** 会议建文档未校验返回结果就记已归档；agent_jobs 忽略 stats.ok 也记 last_run；进度收尾不区分成功失败。需增加可核验的结果状态。
- **平台一致性：** 授权、profile 同步及 `feishu/client.py:run_lark_cli` 已统一解析 Windows launcher；评论已有两条真实请求回读验证，异常边界与调度仍需线上实测。
- **消息与任务可靠性：** 缺 message_id 去重、有限并发队列、取消、持久任务状态和重启恢复。同聊天的 runtime 虽加锁，完整请求的授权、回复和写状态仍可能交错。
- **状态保存：** JSON 写入缺少完整的原子写及统一并发保护；记忆使用头插却保存末尾 500 条，会丢新留旧，索引也未同步截断。
- **运维验证：** 在实际服务账号下验证 CLI、状态目录可写性、systemd 限制、备份及重启；补齐飞书 scope/事件清单。

### 优先级 2：让团队容易使用和判断结果

增加「帮助/能做什么」「任务状态/取消」「新话题/重置」「记住/忘记/查看记忆」的确定性入口。把修改摘要、来源链接、结果确认和失败原因放进统一回复格式。审计增加请求标识、实际工具结果和资源链接；计数/耗时不等于业务验收。

暂未看到：图片/语音/附件处理、Web 管理后台、完整文档同步 RAG、自然语言通用定时任务管理、多人独立 OAuth、个人 P4 ticket、自动测试构建执行闭环。

## 6. 后续路线比较

建议先修共同的身份、权限和可靠性缺口，然后选择一个高频场景验收，而不是同时增加所有能力。

| 方向 | 第一阶段交付 | 收益 | 成本与取舍 |
|---|---|---|---|
| A：团队文档协作（建议优先） | 找资料 → 带来源回答；周报素材 → 标准文档；明确指令 → 小范围更新并核验结果 | 与默认 docs 模式最接近，策划/美术/程序均能使用 | 需要文档权限、修改回执和真实业务样本；先不扩大个人资源范围 |
| B：P4 研发协作 | 提交摘要 → 指定 CL 评审 → 带代码依据的 bug 定位，先只读试用 | 如果主要痛点在研发同步，团队价值更直接 | 需要真实工作区、P4 protections、背景规则及工作区并发隔离；自动改代码后置 |
| C：多人个人助理 | 每人独立授权 → 自己的日程/任务 → 私聊个人摘要 | 使用频率可能高，但属于更大一轮基础设施建设 | 当前共享身份和全局记忆必须先改，不能靠多写几个提示词完成 |

我的建议是 **A 跑稳一个小组，再接 B 的只读能力**。理由来自现有代码和配置：docs 已是默认入口，研发仍需部署模板，个人身份隔离尚未具备。如果当前最急的是代码评审或 P4 更新日志，可以直接优先 B，而不先扩大文档功能。

建议的验收方式（待讨论，不是已承诺指标）：

1. 从真实工作选 10–20 个问题/操作样本，覆盖查不到、权限不足、重名文档和工具失败。
2. 逐条记录是否完成、是否需要人工纠正、输出是否有来源及实际耗时；变更类必须核验目标和实际结果。
3. 定时任务验证跨月、重启、重复事件和失败路径；身份验证至少覆盖两名成员，确认不会串用资源。
4. 验收通过后扩大场景，再讨论管理界面、附件和更复杂记忆。

下一步讨论的核心问题：未来两周最希望团队拿它完成哪一件事——文档/周报协作，还是 P4 日志与评审？先围绕这个目标确定第一批实际使用者和验收样本。
