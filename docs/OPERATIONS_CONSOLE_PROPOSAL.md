# Assistant 运营后台方案草案

日期：2026-09-10。状态：供讨论的方案，尚未实施。根据用户最新优先级重排：先做清晰的流程日志，再把权限、技能、提示词和工具能力变成可热更新的运营配置，随后完成现状报告中的 P0/P1 缺陷。

本次读取时 HEAD 为 `16a5b2a`，工作区还有其他任务的 lark-cli 兼容性改动。实施前以当时最新代码重新核对，不覆盖那些改动。

## 1. 产品目标

运营同学能独立回答四个问题：

1. 用户提出了什么，助手现在执行到哪一步，卡在什么地方？
2. 它当时使用了哪些指令、技能、记忆和权限，实际调用了什么？
3. 怎样修改行为、调整可用能力，并清楚知道何时生效？
4. 修改后效果是否改善，失败时怎样定位和回滚配置？

展示可观测的执行事实以及简要的决策说明。模型内部隐式思维链不属于可完整读取或披露的运行记录；不得用事后生成的推理文本冒充原始思考。缺失的事件、技能使用证据、耗时或费用明确显示“未采集/不可用”。

## 2. 三种实现路径

| 路径 | 优点 | 代价 | 建议 |
|---|---|---|---|
| 文件编辑器 + 日志查看器 | 最快接上现有 JSON/Markdown | 缺发布一致性、历史版本和真正可控的业务权限，运营仍需理解代码配置 | 仅适合作为临时诊断页面 |
| 在现有 Python/Claude CLI 上增加运营后台 | 保留飞书与 Agent 主链路，新增执行事件、配置版本和能力控制 | 需要接入事件与统一配置，逐步替换裸命令权限 | 推荐 |
| 重写为另一套 Agent runtime/平台 | 可以重新组织所有接口 | 同时改变执行、认证和技能加载，迁移范围大，现有问题难以对照 | 本轮暂不选 |

建议使用 Python API 服务、浏览器后台、SQLite 持久状态和实时事件订阅；前端采用适合表单与时间线的组件结构。具体框架版本在实施时验证并固定。这里需要真实后台数据和执行控制，不能仅做展示用页面。

部署暂按“本机先使用，结构支持未来服务器部署”起草；若选择团队服务器，第一版还需完成多账号登录和资源范围隔离后再开放访问。

## 3. 后台页面

### 会话与执行记录：默认首页

左侧是会话列表：用户、群、最后消息、状态、更新时间；可按失败、处理中、模式、日期筛选。一个会话包含多条请求，一条请求可包含首次执行和授权后的重试。

中间是选中请求的时间线，示例为产品展示样例，不是已有运行记录：

```text
收到请求：整理本周项目周报
已排队 → 开始处理
选择“文档协作”配置，第 12 版
加载提示词，提供 3 个技能，召回 2 条项目记忆
执行说明：先定位本周资料，再生成有来源的摘要
请求工具：搜索文档
权限检查：允许，规则“项目资料查询”
工具结果：找到 3 个候选
请求工具：读取文档 → 返回正文
请求工具：创建周报 → 返回文档链接
结果核验 → 回复发送成功
完成 / 失败 / 部分完成
```

右侧详情区展示脱敏后的参数、结果、实际身份、命中规则、配置版本、关联资源和错误信息。运营默认看到中文业务名，例如“搜索文档”；展开高级详情才显示 lark-cli 命令、tool_call_id 等技术字段。

必须区分：

- “提供了技能”与“有证据表明实际调用/加载了技能”。无法确认时只显示前者。
- “模型请求工具”与“工具已执行成功”。请求事件不能当作执行结果。
- “工具成功”与“用户任务完成”。创建文档后回复失败，属于部分完成，不能自动重做创建操作。
- “配置回滚”与“业务操作撤销”。前者不会删除或还原已修改的飞书资源。

第一版支持筛选、实时更新、展开详情和导出脱敏记录。失败记录可以用于配置调试；自动重放带写入的任务后置，避免重复创建或提交。

### 助手配置

把现有 profile 显示为“助手模式”：文档协作、毕设资料、研发协作。

运营可修改名称、用途、回复风格、业务指令、知识背景、输出格式、启用技能、允许的业务能力、超时和适用群。系统运行约束、凭证和部署目录另设管理员页面。

群聊检索作为独立配置区展示：启停状态、自然聊天软阈值、结构化内容软阈值、单条硬阈值、单轮预算、默认结果数、最多检索轮次和发送人显示名映射。跨群禁止、私聊禁止以及“正文不得二次总结”属于系统边界，不允许运营热修改。

提示词拆成可理解的区块，提供编辑器、变量提示、最终组合预览和版本对比。允许 Markdown 高级编辑，但常见配置通过表单完成。

### 技能库

每个技能显示中文名称、用途、适用场景、所需工具、版本、引用它的模式和启用状态。

运营可以修改技能说明、步骤、输出模板和组合现有能力；发布前检查依赖是否齐全。禁用某个工具时，直接列出会受影响的技能和模式。

“修改技能说明”不自动授予工具权限。包含可执行脚本或新集成的技能由管理员管理，不能借编辑文字更改服务执行代码。

### 工具能力与权限

先把用户关心的动作做成可管理的能力：搜索/读取/创建/更新文档、查询任务/日程、读取本地文件、修改本地文件、查询 P4、提交 P4。

每项能力显示用途、参数结构、实际集成、身份需求、读写性质、可操作资源范围、超时和哪些模式/成员可用。运营可以启停已注册能力、修改允许调整的参数和绑定关系；管理员可以管理新工具定义及适配器。

人员权限分为两组：后台角色（查看者、运营编辑者、管理员）与机器人业务能力。旧 read/edit/submit 标签迁移为可读的能力集合，并明确旧 read 曾允许飞书写入，不能静默改变现有行为。

首版默认：运营可编辑并发布其管理范围内的提示词和技能；扩大工具权限、改变身份或资源范围由管理员执行。用户本人作为首个管理员拥有上述权限。服务器多人模式下需按项目/群控制查看日志的范围。

### 发布历史与系统状态

展示草稿、已发布版本、修改人、修改时间、变更摘要、生效范围及回滚入口。系统状态显示 CLI 可用性、任务队列、授权状态、调度状态和最近失败；显示状态不暴露 token 或 secret。

## 4. 热更新的明确语义

编辑草稿 → 校验 → 发布。发布与业务执行共用同一个已验证版本来源，不依赖同时改多个正在被读取的文件。

- 新请求在开始执行时固定一个配置快照，记录提示词、技能版本、能力策略及身份引用。
- 正在执行的请求继续使用它固定的版本；界面提示哪些请求仍在旧版本上。
- 发布改变权限、身份、模式或提示词时，避免继续使用携带旧指令的 CLI session；通过配置兼容标识切换新 session，并明确显示上下文续接范围。
- 回滚产生一个新的发布版本，后续请求使用它，不覆写历史记录。
- 两人同时编辑通过版本校验提示冲突，不能后保存者静默覆盖。
- 管理员紧急禁用能力时，对下一次工具执行检查即时生效；已提交到外部系统的操作不能保证撤回。普通发布不在执行中扩大权限。
- 非法配置不能发布；后台预览明确给出原因、受影响的模式和缺失依赖。

第一版调试默认使用保存样本或模拟工具，验证提示词组合、路由和权限；真实业务试跑需明确展示是否会写入，不能把读取样本回放变成重复业务执行。

## 5. 技术边界

### 执行事件

所有入口共用请求标识：聊天、文档评论、调度任务、后台试跑。快捷指令、排队、授权失败和模式不可用也记录，解决当前只有进入 runtime 才有审计的问题。

最小事件字段为：事件 ID、请求 ID、尝试 ID、会话引用、顺序号、时间、事件类型、来源、配置版本、状态、脱敏内容。工具事件带 tool_call_id 用于匹配请求和结果；身份字段保存引用和校验结果，不保存凭证。

事件先持久化再通知页面；页面刷新或断线可按游标补读。大结果截断时明确显示截断状态，受控附件保存完整的允许留存内容。后台权限同样适用于导出和附件下载。

### 配置与状态

SQLite 存储请求、事件、配置版本、发布历史、后台用户和任务状态。运行配置通过统一服务获取；旧 JSON/Markdown 作为导入来源，导入前备份，保留原文件，不在本轮直接删除。

现有 CLAUDE.md、settings 和 skills 编译为执行所需的受控配置。运行时不能被全局用户配置或项目目录里的额外规则悄悄扩大权限；必须验证实际加载来源。后台显示的“生效配置”必须与 CLI 实际收到的一致。

### 工具执行控制

工具能力需要由执行层落实。裸 `Bash(lark-cli:*)` 无法直接等同于“只允许查文档”等业务开关。对已注册业务动作采用结构化参数和统一执行适配器；未注册动作明确拒绝或交管理员增加能力。

保留 Claude CLI 的原生工具循环；通过可验证的事件和执行前检查接入日志与策略。官方提供工具执行前/后及失败 hooks，可作为接入候选；必须先用本机安装版本验证格式、失败行为和覆盖范围，不能假定 hooks 本身就是完整沙箱。参见 [Claude Code hooks 官方文档](https://code.claude.com/docs/en/hooks)。

执行策略至少保证：参数校验、真实身份、资源范围、能力开关、固定版本和紧急禁用。凭证由服务端注入，不由模型或运营提示词指定；为禁用能力保留等价的通用 API/任意 Shell 入口会使权限失效，验收必须覆盖这种绕路。

## 6. 实施顺序及交付边界

### 第一批：先看清楚每次执行

交付真实请求列表、时间线、参数与结果、错误状态、配置来源快照、筛选及实时更新。补最基本的后台访问控制和脱敏，保持已有飞书入口行为可对照。

验收：私聊、群聊、快捷命令、授权失败、超时、工具拒绝、调度和评论都有可追踪记录；刷新页面不丢进度；未采集数据不被伪造；外部操作成功但回复失败可辨认。

### 第二批：运营能改变下一次执行

交付提示词编辑、技能库、工具能力开关、群与成员规则、草稿发布、热更新、版本对比和回滚。配套执行层校验，不交付只有界面开关的假权限控制。

验收：不重启机器人即可改变下一请求的行为；运行中请求版本不漂移；发布冲突不丢改动；禁用能力确实无法执行；配置回滚可验证。

### 第三批：完成 P0/P1 修复与验收

P0：用户授权与 sender 绑定、群/用户/项目记忆和会话隔离、调度管理员权限、工作区及工具权限、多群共享 P4 工作区并发保护。第二批依赖的权限修复随第二批一并完成，不等到开放后台之后。

P1：跨月调度、到期日判断、业务错误与空数据区分、成功状态与核验、Windows 通用 CLI 入口、请求去重、有限并发与取消、重启后状态恢复、原子保存、记忆保留和索引一致、部署环境及备份验证。

每项先复现或构造有意义的回归测试，再修复。历史清单中的“输出格式强制”和“共享搜索身份选择”正在由其他任务调整，需按最新代码复核，不能重复覆盖。

多人 OAuth 的最终存储/隔离方法需先验证 lark-cli 支持方式。验收目标是两名成员不会串用身份；若当前适配器不支持，应明确禁用不匹配的个人查询，不能把共享身份继续伪装成逐人授权。

### 总体验收

1. 用户能从失败结果追溯到实际工具输入、返回、身份与配置版本。
2. 运营不编辑服务器文件，就能发布提示词/技能并看到下一次请求采用新版本。
3. 权限关闭后的工具操作在真实执行入口被拒绝并留下原因。
4. 两名成员、两类群以及一个共享工作区的隔离和并发用例通过。
5. 跨月、失败、重复事件、取消及重启恢复有回归覆盖；外部副作用不自动重复执行。
6. 文档清楚区分模拟验证、CLI 集成测试和真实飞书/P4 验收结果。

## 7. 当前需要收敛的产品选择

建议选择上述第二条实现路径，按三批推进。部署选择正在询问：先本机，还是直接提供团队服务器多人访问。该选择决定第一批后台登录和部署验收的范围，不影响执行事件与配置版本模型。

本草案用于确认范围；确认后再拆实施计划，不将未确认方案写成已完成功能。
