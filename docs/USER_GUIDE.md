# Assistant 操作手册

核对日期：2026-09-19。完整能力边界见[功能现状](STATUS_AND_ROADMAP.md)。

## 1. 普通用户怎么用

私聊机器人直接发送文字。群聊必须通过飞书 @ 选择当前机器人；仅输入它的名字或 @ 其他人不会触发。以下群聊示例均省略前面的 @。

| 场景 | 可以发送的请求 | 前提或结果 |
|---|---|---|
| 看自己的权限 | 我的权限 / 查看权限 | 返回群模式及 read/edit/submit 层级 |
| 看调度状态 | 查看配置 | 返回摘要时间、推送目标、归档、提醒和启用任务数量 |
| 找资料 | 搜索《卦阵手记》的战斗循环文档，给我标题和链接 | 需要相应飞书访问权限；搜索可能触发用户授权 |
| 读文档 | 总结这份文档：<飞书链接>，列出当前结论和未解决问题 | 通过 lark-cli 读取；不是上传文件解析 |
| 修改文档 | 把这份文档的“本周进展”更新为：……，保留其他部分 | 需要资源写权限；多候选时按规则先选择目标 |
| 创建文档 | 新建“本周周报”，内容如下：…… | 可能实际创建飞书文档 |
| 查个人信息 | 查看我的今日日程 / 列出我的待办任务 | 目前共用用户登录身份，不能保证对应每位提问者，见第 2 节 |
| 清除会话 | 清除上下文 / 重置会话 / 新建会话 / 切换会话 | 清除当前私聊或当前群共享的 Claude 上下文及关联记忆；询问“怎么清除”或表达“想重新开始”时会先引导发送明确命令 |
| 项目信息积累 | 小王负责战斗 UI，本周计划完成技能面板 | 简单规则可能抽取为当前私聊或当前群的会话记忆 |
| 研发查询 | 总结本周 P4 提交，按新增、修复、优化分类 | 需 dev 模式和已配置 P4 工作区 |
| 代码评审 | 检查 changelist <编号>，列出问题、位置和建议 | 需 dev 模式；评审由 Claude + p4 工作流完成 |

复杂请求建议一次给清楚目标、素材、需要的输出和是否修改源文档。同一聊天会续接上下文；需要从空白上下文重新开始时，单独发送「清除上下文」「重置会话」「新建会话」或「切换会话」。目前没有处理中取消任务命令。

处理时可能先出现思考表情；发生工具调用后会显示进度，约每 3 秒更新，最后发送结果。进度上的「完成」仅表示流程收尾，仍需看最终正文判断操作是否成功。

### 群聊记录按需检索

群内没有 @ 机器人的消息不会触发回复，但会写入当前群的本地历史库。机器人被 @ 后，如果问题存在未解析指代、要求结合群内讨论，或 AI 判断现有信息不足，可以主动检索当前群记录。关键词只作为参考；信息充分时不会固定携带历史消息。

检索范围由 Python 宿主绑定为当前群，模型不能指定其他群。私聊不能读取群聊库。回复群消息时会把父消息和同一回复链作为优先范围。返回给 AI 的普通消息格式为 `[时间 姓名] 原始正文`，正文不经过第二次总结、合并或润色。超长日志、转发结构或代码会明确标记为原文片段，AI 最多按配置继续展开；触发问题本身会从检索结果中排除。

### 文档评论与连续追问

评论默认简短：100–200 字、最多 3 条要点。AI 判断需要详细论证、完整改写或方案对比时，会创建说明文档，回读确认后在评论中留下结论和链接；同主题追问优先补充已有说明文档。建文档或授权失败时简短说明，不回贴整篇长文。规则由 `profiles/docs/.claude/skills/comment-reply/SKILL.md` 维护，Python 每轮注入。

飞书助手所有模式的主调用及子任务模型统一固定为 `deepseek-v4-flash`，包括旧会话续接；不自动回退 Pro。API 地址与凭证继续使用启动环境的配置，需支持该模型。该限制作用于本助手，不修改个人 Claude 的全局默认设置。

在文档中选中一段文字，添加**未解决的局部评论**，通过飞书的 @选择器选中机器人，并写下指令。处理结果会回到同一评论线程。

例如：先发送「@机器人 帮我润色这段」，收到回复后，在该线程紧接着发送「再短一点」，无需再次 @。如果中间已有其他人回复，或你在回复中明确 @其他人，请重新 @机器人来继续调用。不同评论线程上下文独立，同一线程的参与者共享上下文。

同一文档的请求会排队执行，目前没有处理中回执。2026-09-12 实测单次审阅执行约 137–158 秒，后一条叠加排队后约 253 秒收到回复；这是样本耗时，不是响应时限。排查时应结合审计与原线程最新回复判断，不能仅凭暂时没有回复认定事件未到达。

纯 @会收到补充指令提示；普通新评论不触发。全文评论和已解决评论目前不执行，不能用它们验证回复功能。评论处理仅用机器人身份，需要它有读取评论、回复评论及目标文档的相应访问权限。首次接入还需在开放平台订阅 `drive.notice.comment_add_v1`、发布权限变更，并检查 bot 的云文档通知订阅状态：

```powershell
lark-cli --profile assistant-bot --as bot drive user subscription_status --event-type drive.notice.comment_add_v1
```

若 `is_subscribe` 为 false，管理员在确认应用及权限正确后，用 `drive user subscription` 开启该事件的用户/应用维度订阅；这一步不同于本地 SDK 注册回调。按 `lark-cli schema drive.user.subscription` 查看参数。

验收顺序：@总结选中段落 → 等机器人回复 → 无 @追问「再短一点」 → 新建另一条无 @评论（不应触发）。日志应有 `[DOC] received`，随后首次出现 `accepted gate=mention`、追问出现 `accepted gate=followup`。

## 2. 用户授权怎么用

普通共享资源优先使用 bot 身份。识别到个人日程、任务、会议等需求时，会先检查用户登录；bot 操作明确需要 user 时，也可由 Agent 返回标记触发授权。

1. 需要授权时，机器人将链接发到触发请求的会话中。
2. 打开飞书授权页面并完成确认；程序不会自动打开本机浏览器。
3. 成功后继续原请求。bot 失败后的授权回退最多重试一次。
4. 失败或过期时，查看返回提示，之后重新发送请求。

当前授权使用 lark-cli profile；个人资源必须确认用户身份。日历读取还需要飞书应用开通 `calendar:calendar.event:read`，缺少时会明确提示管理员开通后重新授权。团队试用应先确认应用权限和授权归属。

## 3. 调度命令速查

这些是 Python 直接识别的固定指令，不消耗一次 Claude 推理调用。

| 指令 | 效果 |
|---|---|
| 查看配置 / 当前配置 / 调度状态 / schedule status | 查看调度配置 |
| 推送到这里 | 将当前会话设为每日摘要和任务提醒的共同目标 |
| 开启每日推送 / 关闭每日推送 | 切换每日摘要 |
| 推送时间 09:30 | 修改摘要时间，使用服务所在机器的本地时区 |
| 开启会议归档 / 关闭会议归档 | 切换会议归档轮询 |
| 开启任务提醒 / 关闭任务提醒 | 切换到期提醒 |

默认每日摘要 09:00、会议检查每 60 分钟、任务提醒每 3 小时。摘要最多列 5 条日程、5 条任务、3 条相关记忆。未设置推送目标时，摘要和任务提醒不会发送；会议归档有独立开关，不以推送目标为前提。

目前这些设置是**全局共享**，没有按群分别保存，也没有管理员身份校验。任何能触发机器人的用户都能执行这些命令，包括覆盖推送目标。

## 4. 管理员：本地启动

需要 Python、`requirements.txt` 中的依赖、可用的 Claude CLI 和 lark-cli。启用研发模式还需要 p4 CLI、工作区和登录票据。

从 `assistant` 的父目录运行，下面的值均为占位符：

```powershell
python -m pip install -r assistant/requirements.txt
$env:FEISHU_APP_ID = '<飞书应用 App ID>'
$env:FEISHU_APP_SECRET = '<飞书应用 App Secret>'
python -m assistant.main
```

Claude 的认证由 Claude CLI 自身处理。Python 不要求 `ANTHROPIC_API_KEY` 必填；先确认服务使用的系统账号能正常运行 Claude。

程序启动会先同步 lark-cli profile 的应用凭证，再获取机器人 open_id，随后启动调度器和 WebSocket。无需为了普通 bot 操作预先执行用户 OAuth；按需授权已接入聊天流程。

`run.ps1` 和 `start-assistant.bat` 只负责切换目录和启动，不自动加载 `.env`。双击启动时需要凭证已在其继承的环境中配置。结束前台进程可用 Ctrl+C。

飞书应用应启用机器人和长连接事件接收，配置可用范围及业务资源权限。代码注册的事件有 `im.message.receive_v1`、`im.message.recalled_v1`、`drive.notice.comment_add_v1`，以及 reaction 创建/删除事件；reaction 事件仅空处理。群聊历史功能需要应用订阅消息接收和撤回事件，并开通“接收群聊中所有消息”权限 `im:message.group_msg`；只有 `im:message.group_at_msg:readonly` 时通常只能收到 @ 机器人的群消息，无法形成完整群聊记录。权限变更后需要发布应用版本并重新验证事件投递。

启动后先私聊「我的权限」，再在群里 @ 机器人发送同样命令。若日志提示无法获取机器人身份，群消息全部忽略，但私聊仍会进入处理。

## 5. 管理员：群模式与成员权限

默认数据目录为 `assistant/data/`，可用 `ASSISTANT_DATA_DIR` 修改。管理员编辑其中的 `runtime_config.json`：

```json
{
  "default_profile": "docs",
  "chat_profiles": {"oc_实际研发群ID": "dev"},
  "default_tier": "read",
  "user_tiers": {"ou_实际成员ID": "edit"}
}
```

该文件每次 runtime 调用重新读取，无需重启。普通 Agent 请求的审计记录有 chat_id 和 sender；「我的权限」「查看配置」等快捷命令不会进入 runtime 审计。

| 模式 | 工作位置 | 准备事项 |
|---|---|---|
| docs | `profiles/docs/` | 默认模式，使用 lark-cli 操作飞书 |
| thesis | `THESIS_DIR` | 设置目录，在目标目录部署 thesis 的规则及 `.claude` 配置 |
| dev | `P4_WORKSPACE` | 配置 P4 登录和 protections，在目标目录部署 dev 模板并填写项目背景 |

runtime 对 thesis/dev 仅切换 cwd，不会自动复制模板。目标目录如果已有 `CLAUDE.md` 或 `.claude`，先合并规则，不要直接覆盖。修改环境变量需要重启服务。

群聊检索配置位于同一数据目录的 `group_history_config.json`，每次检索重新读取，无需重启：

```json
{
  "enabled": true,
  "natural_soft_chars": 3000,
  "structured_soft_chars": 2000,
  "hard_chars": 12000,
  "retrieval_token_budget": 6000,
  "default_limit": 8,
  "max_search_rounds": 2,
  "sender_names": {"ou_实际成员ID": "张三"}
}
```

事件没有提供显示名时，系统先查 `sender_names`，仍未命中则显示 open_id。配置无效时保留进程内最后一次有效版本并记录错误。群聊原文数据库为 `group_history.sqlite3`，不要通过直接编辑数据库调整内容。

| 层级 | 主要含义 |
|---|---|
| read | 禁止本地 Edit/Write 和 P4 修改；仍可经 lark-cli 创建、更新飞书文档 |
| edit | 在模式许可下改本地文件、p4 edit/add；不允许 p4 sync/submit |
| submit | 在模式许可下允许 p4 sync/submit |

**read 不是飞书资源只读。** 各层级都叠加禁止部分 P4 危险命令；这些是 CLI 权限规则与行为约定，不能仅凭 cwd 宣称实现了操作系统级文件隔离。

默认 lark-cli profile 是 `assistant-bot`。环境变量虽可修改名称，但各模式说明中仍写死这个名称；使用自定义名称前需同步核对 Agent 规则。

## 6. 管理员：定时 Agent 任务

编辑数据目录的 `scheduler_config.json`，保留现有配置，在 `agent_jobs` 数组添加条目。例如先在已经完成配置的 dev 环境里试运行只读摘要：

```json
{
  "name": "weekly_changelog",
  "enabled": true,
  "profile": "dev",
  "chat_id": "oc_实际目标群ID",
  "day_of_week": 4,
  "hour": 17,
  "minute": 0,
  "prompt": "读取本周 P4 提交，按新功能、修复、优化生成摘要并引用 changelist 编号。"
}
```

`day_of_week` 的 0–6 为周一至周日。文件手动修改后重启服务；聊天配置命令才会更新内存并即时重排。没有自然语言任意创建定时任务的专用接口。

任务以空 sender 调用 runtime，通常继承默认 read 层级。调度链路没有聊天入口的授权预检和重试；资源身份须预先配置。当前也没有持久化任务队列、错过时间补跑及失败重试机制。

## 7. 常见问题与维护

| 现象 | 优先检查 |
|---|---|
| 启动即退出 | FEISHU 两项环境变量、lark-cli 是否可执行、配置同步日志 |
| 私聊有反应，群里没反应 | 是否真正 @ 当前机器人、bot open_id 获取结果、应用可用范围 |
| 提示模式未配置 | THESIS_DIR / P4_WORKSPACE 是否设置、目录是否存在 |
| 「我的任务」身份不对 | 当前 profile 的 user 登录归属和 sender 绑定；不匹配时应拒绝执行 |
| 日历读取被拒 | 请管理员在飞书开放平台开通 `calendar:calendar.event:read`，再重新授权 |
| 授权后仍提示权限不足 | 日历会校验并提示缺少的 scope；其他能力仍需管理员检查应用权限和用户授权 |
| 无定时推送 | 服务是否常驻、引擎是否运行、目标会话、开关、本机时区 |
| 摘要说没有任务，但实际上有 | API/CLI 错误可能被包装为空列表，不能仅以摘要判断数据为空 |
| Windows 的评论回复或调度失败 | launcher 已统一解析；检查 PATH 中的 lark-cli、profile、权限和 `[DOC] failed` 日志 |
| 文档 @后没反应 | 无 `[DOC] received`：检查开放平台事件订阅、通知订阅状态及是否运行了新版本；有 received 但被忽略：检查收件人/作者 ID、是否全文或已解决评论 |
| 无 @追问没反应 | 必须是同线程紧接机器人回复、没有明确 @其他人；检查是否收到 add_reply 通知，日志中的 to 是否为机器人 |
| 修改完成但回复失败 | 后台最多重试 3 次；待发结果保存在 `data/doc_comments.sqlite3`，同事件重投只补发；不要通过删除去重库强制重做写操作 |
| 群里换人追问却丢失前文 | 群会话按 `group:<chat_id>` 共享；检查是否换了群，以及是否有人发送了清除会话命令 |

Linux 的路径规划、systemd 文件参见[部署指南](../deploy/README.md)。模板尚需真实服务账号验收：包括 CLI PATH、认证文件可写性，以及 `ProtectHome=read-only` 与 CLI 保存状态的兼容性。

`data/` 保存会话、记忆、配置和审计；Claude 自己的会话数据及 lark-cli 授权数据不在这份目录内。维护备份需覆盖这些独立状态并控制访问权限。仓库尚无自动备份、恢复或日志轮转工具。
